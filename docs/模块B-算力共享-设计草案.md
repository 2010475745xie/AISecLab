# 模块 B —— 算力共享（设计草案）

> 状态：**草案，未拍板、未写代码**（2026-10-12）
> 定位：与 **AISecLab 是两个独立模块**，做在**同一个 App** 里，**互不 import**。
> 本文只描述模块 B 自己，不涉及模块 A 的任何改动。

---

## 0. 一句话与主轴

把同一局域网内愿意出力的设备（手机 / PC）组织成一个**共享推理池**，
任何设备都能通过一个 **OpenAI 兼容端点**使用池里的模型 —— 人人贡献、人人可用。

**本文的主轴（也是初版方案被推翻的地方）：**

> 共享的不是「同一个模型的算力」，而是「**不同任务落到不同能力设备**」的能力。

只要按**任务类别**切分，手机能不能贡献就不再取决于它能不能装下 7B。
初版判断「PC 出算力、手机消费」只看到「手机装不下 7B」，把**模型规模**错当成了**能否贡献的唯一轴**。

## 1. 与模块 A 的边界

| | 模块 A（AISecLab） | 模块 B（算力共享） |
|---|---|---|
| 职责 | 用例 / 判定链 / 评分 / 报告 | 节点注册 / 调度 / 模型注册 / 推理服务 |
| 代码关系 | **完全不动** | **互不 import** |
| 共用面 | App 壳：导航、设置、Key 管理、网络层（EncryptedSharedPreferences + OkHttp/SSE） | 同左 |

**唯一联动方式：靠标准协议松耦合。**
模块 B 对外暴露一个 **OpenAI 兼容的 `base_url` + key**；模块 A 把它当成「一个普通被测模型端点」填进 CONFIG 表单即可。
不共享代码、不共享数据模型、不共享判定逻辑。

## 2. 设备能力分层 × 任务类别（核心）

**贡献 ≠ 跑同一个模型。** 设备按「能装下多大的模型」分层，调度器按**能力标签**派单：

| 设备档位 | 可常驻的模型 | 可接的任务类别 |
|---|---|---|
| 手机 · 低功耗档 | 0.1B~0.5B | 文本嵌入、语义去重、分类打标、prompt 预处理（分词 / 前缀缓存） |
| 手机 · 全速档 | 0.5B~3B（Q4） | 上述全部 + 小模型补全、简单问答 |
| PC · 常规 | 7B~13B（Q4/Q5） | 主推理、生成长文本 |
| PC · 带 GPU | 13B+ / 多卡 | 主推理、调度器、**抽样复算仲裁节点** |

Android 单进程内存上限 2~4GB，7B Q4 权重 + KV cache 就要 4GB+，**装不下就是装不下** ——
所以手机本来就不该接 7B 的活。这不是限制，是分层。

> 由此得到一个直接结论：**同一个模型可以有异构节点，只要它们能装下。**
> 模型注册表按模型规模天然实现了能力分派，不需要另写一套设备打分逻辑。

## 3. 贡献档位（用户可调）

「用户可以选择自己贡献多少算力」拆成**三个独立旋钮**，而不是一个滑块：

| 旋钮 | 取值 |
|---|---|
| ① 速率 | 并发数 / 限频（单核 ~ 全速）/ 单任务时长上限 |
| ② 触发条件 | 充电时 / 息屏时 / 仅 Wi-Fi / 仅局域网 / 指定时段（如 00:00–08:00） |
| ③ 资源上限 | 可常驻内存（决定能接哪一档模型）/ 单日流量上限 |

**档位（预置组合，用户也可微调）：**

| 档位 | ① 速率 | ② 触发 | ③ 上限 | 默认给谁 |
|---|---|---|---|---|
| 0 · 关闭 | — | — | — | 手动关闭 |
| 1 · 零打扰 | 限频 1 并发 | 充电 + Wi-Fi + 息屏 | 0.5B / 200MB 日 | **手机默认** |
| 2 · 全速 | 全核 | 前台或充电 + Wi-Fi | 3B / 不限 | 用户主动升 |
| 3 · PC 档 | 多并发 | 不限 | 13B+ / 不限 | **PC 默认** |

> **默认值拍板**：手机默认档位 1（零打扰），PC 默认档位 3。
> 理由：手机默认必须是「用户感觉不到」的档，升档由用户主动做。
> 若默认就给全速，第一次发热降频 + 流量提醒就会把用户赶走。

## 4. 手机的三个隐性成本（初版漏掉的）

| 成本 | 具体量级 | 对应机制 |
|---|---|---|
| **流量** | 一个 3B 量化模型权重就是 GB 级；手机流量敏感 | 仅 Wi-Fi 触发 + 日流量上限 + 权重只下载一次并校验 hash |
| **热与电** | 持续推理必然发热降频 | 读 Android `ThermalStatus`，超温**自动降档**并在界面明示 |
| **可靠性** | 随时切后台 / 息屏 / 断网 / 被系统杀 | 任务必须**短、无状态、可幂等重派** |

第三条是设计约束，不是运维细节：**任务颗粒度必须按「丢了也不心疼」来切。**
好消息是「重派便宜」正是小任务的好处 —— 手机接的本来就是短任务。

## 5. 请求路由：一次推理怎么落到节点

```
用户请求 (OpenAI 兼容: POST /v1/chat/completions)
   ↓
模型注册表：model_id → (权重 hash, 量化, 参数量, 最低常驻内存, 支持的档位)
   ↓
能力过滤：只在「能装下该模型 且 此刻在接单」的节点里选
   ↓
在候选集内按 负载 / 延迟 / 贡献额度 排序 → 派单
   ↓
节点本地推理 → 回「原始输出 + model hash + 采样参数」
```

**模型注册表条目（字段口径，先定死）：**

```
model_id            模型标识（如 qwen2.5-1.5b-instruct-q4_k_m）
weights_hash        权重文件 sha256 —— 不一致视为不同模型，绝不允许混用
quant               量化格式（q4_k_m / q5_k_m / fp16 …）
params_b            参数量（十亿）
min_ram_mb          最低常驻内存
min_vram_mb         最低显存（0 = 纯 CPU 可用）
node_tiers          允许接单的档位集合（如 ["phone_full","pc"]）
```

`weights_hash` 是硬门槛：不同量化版本不是同一个模型，混在一个池子里会让「同一个模型名」
输出不同质量的结果，且无法归因。

## 6. 记账与激励

**核心约束：用户自报的档位 ≠ 真实贡献。**
把档位拉到最大然后摸鱼，成本为零 —— 所以 credit **不能按自报 FLOPs / 自报时长**计。

**拍板：记账单位 = 「通过抽样复算验证的输出 token 数」。**
理由：防作弊本来就要做抽样复算（§7），一套机制两用，不额外增加开销。

**消费额度：**

- 新设备赠初始额度 —— 解决冷启动「没贡献就没额度，没额度就没法用」的死锁；
- 允许 消费 > 贡献，到**软上限**后：降级到小模型（手机本地就能跑的那种）或排队，而不是直接拒绝；
- 额度是**产品话术**，不是计费系统：目的是让「贡献」有意义，不是精确结算。

## 7. 信任模型

模块 B **不产判定**，输出就是文本，所以信任问题的量级比挂在判定链上低得多。
但仍要处理「节点回了个假回答」：

- **抽样复算**：随机抽 x% 的任务派给两个节点，输出不一致 → 转给 **PC 档 / 仲裁节点**重算，
  并降低该节点的可信度分。代价 = 算力 ×(1+x)，x 取 5%~10% 起步。
- **不做的事（明确划掉）**：TEE / zkML 在手机与消费级 PC 上目前不现实，不列入设计。
- **界面诚实**：显式展示「信任模式」，不假装安全。

## 8. 网络拓扑

**拍板：第一版只做局域网（同一 Wi-Fi 网段 / 有线）。**

理由：跨公网必须打洞（WebRTC / QUIC）或中继，而**中继的出口带宽成本很可能直接超过买 API 的钱** ——
一个纯本地推理池为了省 API 费，先付出一笔更大的带宽费，商业上不成立。
另外公网 P2P + 生成式内容流转涉及备案与内容安全责任，局域网自建组网规避这一层。

二期再考虑：自建 VPN（WireGuard）/ Tailscale 之类的 overlay 组网，仍然不是公共 P2P。

> ⚠️ 已知落地坑：手机与 PC 同网段却连不上，常见原因是**无线客户端隔离**（AP 侧禁止客户端互访）。
> 判据是 ARP 表为空。App 里要给一条明确的自检提示，别让用户以为是软件 bug。

---

## 9. PC 端形态

**拍板：PC 侧第一版做「独立节点程序」（CLI + 极简本地面板），不做 Windows 版 App。**

理由：PC 端不需要 App 壳那套导航 / 设置 / 报告 UI，做 Windows 版要么把 Android 项目迁到 KMP
（代价远超收益），要么维护两份 UI。独立节点程序 + 同一份协议，成本最低，且 App 里能看见它、能派单给它。

## 10. 分期落地（建议）

| 期 | 内容 | 验收 |
|---|---|---|
| 一期 | 局域网节点注册 + 模型注册表 + 单模型（PC 7B）OpenAI 兼容端点 + 贡献档位 0/3 | PC 上跑起节点，手机 App 填 base_url 能正常对话 |

| 四期 | overlay 组网（跨网段） | — |

## 11. 风险（不藏）

1. **功耗是物理事实，档位不能消除它。** 手机默认档位 1 下真实贡献量很小，
   所以「人人贡献、人人用」在经济上仍可能不成立 —— credit 制度能缓解搭便车，
   但改变不了「手机单位算力的电费 / 发热成本高于 PC」。这一条大概率会决定池子里的真实供给结构。
2. **冷启动空池**：只有一台设备时，池子等于没有。第一期实际上是「单节点服务」，
   要到二期设备数上来了才算真的共享。
3. **异构带来的调度复杂度**：能力标签一旦引入，调度器就不再是「在线 / 离线」二值，
   测试面明显变大。
4. **与模块 A 的隐私承诺无关**，但用户可能误以为有关 —— 界面需要在模块 B 内部说明
   「你的请求会离开本机、发到同网段的其他设备上执行」，这句话不能省。
