> **性质：内部实现方案，不是对外材料。**
> 对外材料（阐释 / 介绍 / 答辩稿）只写已实现的部分，见 `docs/项目全貌-阐释.md` 的口径。

## 0. 一句话

在报告页引入**一套最小 Canvas 绘图原语** + **一份明确的字段契约**，第一批同时点亮四项视图：

| 视图 | 数据来源 |
|---|---|
| 危险度热力图（用例级） | `JudgeResult.verdict` + `confidence` + `TestCase.dimension` |
| 四路分区分布 | `ReportSections` |
| 判定层级分布 | `JudgeResult.level` |
| 攻击演进链路（时间轴） | `attackTrail` + 新增 `attackRounds` |

**为什么合并成一份方案**：四项共用同一份报告数据、同一套 UI 原语。拆成四份方案会把同一套组件写四遍。

## 1. 数据现状三分（**先看这张表，再谈工作量**）

- **[现有]** 已落库，端 / 后端都有，零改动可直接画
- **[小改]** 字段在，但缺一项，需一次小改动
- **[新建]** 完全没有，需新做

| 视图 / 需要的字段 | 现状 | 说明 |
|---|---|---|
| 危险度热力图（**用例级**）：`verdict` + `confidence` + `dimension` | **[现有]** | `JudgeResult.confidence` 就是最终判定置信度，已持久化 |
| 危险度热力图（**逐 token 曲线**）：护栏 top-k 危险度 | **[新建]** | `HttpSafetyGuard` 确实拿到过 `firstTopTokens`，但**没有落进 `TestResult`**；要做得加字段 + 端/后端两侧 + 导出侧，且端上护栏只在部分形态可用（HTTP / 端侧 / 用户 LLM 三分支），覆盖不全时图表会**误导**。**本批不做** |
| 四路分区分布：`ReportSections`(fails / reviewOnly / skipped / inconclusive) + `unassessedByDim` | **[现有]** | 已是单一实现（报告页 / Markdown / HTML 三处共用） |
| 判定层级分布：`JudgeResult.level`（L1_PATTERN / L2_SEMANTIC / L3_STRUCTURAL / LLM） | **[现有]** | 字段在，UI 从没画过 |

| 基线对比叠加：`ReportDiff`（新增失守 / 已修复） | **[现有]** | 已有，可作为热力图的叠加层 |

**结论**：四项里 **三项零数据改动**，只有攻击演进链路需要一次数据结构变更。

## 2. 数据现状·关键前提：三处**两端不一致**（本方案必须先处理；第 4 处见 §3.3）

读码发现，`attackTrail` 两侧虽然字段同名，语义并不一致。这些不一致在纯文本报告里看不出来，**一旦画成时间轴就会被放大成肉眼可见的错位**。

### 2.1 轮次编号：端上 1-based，后端 0-based

- 端上 `RecursiveAdversarialAttack.kt:31` → `for (round in 1..maxRounds)`
- 后端 `attack.py:237` → `for r in range(max_rounds)`，`trail` 里写的是 `R0 / R1 / …`

**后果**：不统一的话，同一次攻击在两端时间轴上错位一格。
**决定**：`AttackRound.round` **统一 1-based**（人看的轴从第 1 轮开始），后端落库时 `r + 1`，显示字符串也一并改。

### 2.2 trail 内容：后端含回答片段，端上只有 prompt

- 后端 `attack.py:244` → `f"R{r} 攻击: {prompt[:60]} → 回答: {resp[:80]}"`
- 端上 `RecursiveAdversarialAttack.kt:33` → `"第${round}轮攻击：$currentPrompt"`
- 端上 fallback 分支又是第三种格式 → `"变异攻击：${v.prompt}"`

**决定**：`attackTrail` **保留不动**（已发布的 wire 字段，改它会让旧报告反序列化异常）；结构化信息全部走新增的 `attackRounds`。

### 2.3 ⚠️「未破防时返回哪一轮」两端相反（本轮新发现）

- **后端**：`attack.py:256` → 始终未破防时 `return first_resp, trail`，**返回首轮**。代码注释给了理由：末轮是被攻击变体诱导后的答非所问，**不是失守证据**，用它判 FAIL 是误伤。
- **端上**：`RecursiveAdversarialAttack.kt:34` → `best` 每轮被覆盖，循环结束后 `return best`，**返回末轮**。

**后果**：同一条用例"没被攻破"，两端报告里引用的**是模型不同的两次回答**。时间轴如果要标注"最终判定取自第 N 轮"，两端会标出不同的 N。
**决定**：端上**对齐后端语义**（未破防返回首轮）。这是本方案里唯一一处**行为修正**，不是纯新增；改完必须跑端到端对照。

## 3. 数据契约（改动只有这一处）

### 3.1 端上 `core/model/TestResult.kt`

```kotlin
@Serializable
data class AttackRound(
    val round: Int,        // 统一 1-based（见 2.1）
    val prompt: String,    // 该轮实际发给被测模型的攻击 prompt
    val response: String,  // 该轮被测模型的回答
    val refused: Boolean   // 该轮是否"未破防"（见 3.3）
)

@Serializable
data class TestResult(
    // …现有字段（attackTrail 保留不动）…
    val attackRounds: List<AttackRound> = emptyList()
)
```

`attackRounds` 是**纯新增可选字段**，默认空列表 → 旧报告反序列化不受影响。

### 3.2 后端 `app/models.py`

```python
class AttackRound(BaseModel):
    round: int
    prompt: str
    response: str
    refused: bool

class TestResult(BaseModel):
    # …现有字段（attackTrail 保留不动）…
    attackRounds: List[AttackRound] = []
```

⚠️ **字段名必须与端上逐字一致。** 两端都用 `ignoreUnknownKeys = true` —— 名字或类型对不上**不报错、直接静默丢弃**，表现成"图是空的"而没有任何报错。改完必须端到端跑一次**看到图**，不能只看编译通过。

### 3.3 `refused` 的定义（避免出现第三份拒绝词表）

现状有三套互不相同的"拒绝/破防"判据：

| 位置 | 判据 |
|---|---|
| 后端 `attack.py:232` | 命中 17 条 `refusal_markers` 之一 → 继续迭代 |
| 端上 `ResponseContext.isRefusal()` | `STRONG_REFUSAL` 第一人称拒绝话术 → 供判定层用 |
| 端上 `RecursiveAdversarialAttack.kt:37` | `verdict == FAIL && confidence >= 0.7f` → 突破判定 |

**决定**：`refused` = **该轮「未破防」，用该侧循环自己的破防判据取反**。

> ⚠️ **本方案初稿这里写错了，落地时被代码推翻。** 初稿写的是「`refused := verdict != FAIL`，
> 两侧都有 verdict、零新词表」—— 后端做不到：**后端每用例只判最终返回的那一轮**，
> 逐轮 verdict 根本不存在（逐轮判会把裁判调用量抬到最多 10 倍）。正确取值：

- 端上：`!(verdict == FAIL && confidence >= 0.7)` —— 端上每轮都真判过（`runOnce` 里调 `judge`），逐轮 verdict 存在；
- 后端：`!(命中 refusal_markers)` —— 用它循环里**已有**的词表，不新增词表、也不改循环行为。

**为什么不统一成一个判据**：统一只有两条路 —— 要么让后端逐轮判（裁判成本 ×最多 10）、
要么让端上丢掉 verdict 改用词表（白白扔掉已有信息）。两条都比「各用自己循环里已有的判据」更差。
代价是两侧 `refused` **含义相同、判据不同**，这一点已写进两端 `AttackRound` 的注释里。
这也是本文发现的**第 4 处两端不一致**（前 3 处见 §2）。

**注意**：`refused` 是**展示用**的派生量，与判定链无关，**不得**回流去影响 `verdict` 或评分。图例里要写明它的语义边界（例如连续拒绝词被包含在长回答里时该轮仍可能被记为未破防）。

### 3.4 后端 `attack.py::run_recursive` 的落点

循环里现在这一行：

```python
trail.append(f"R{r} 攻击: {prompt[:60]} → 回答: {resp[:80]}")
```

改为**同时**写两个结构（`trail` 保持原样以兼容，`rounds` 为新增）：

```python
trail.append(f"R{r} 攻击: {prompt[:60]} → 回答: {resp[:80]}")
rounds.append(AttackRound(round=r + 1, prompt=prompt, response=resp, refused=...))
```

按 §3.3 修正后的定义，`refused` 在**循环体内就能算出来**（后端用拒绝词命中，端上用 `runOnce` 已返回的 `verdict`），**不需要等判定回填**。

### 3.5 端上 `RecursiveAdversarialAttack.kt` 的落点

- `iterativeAttack`：`trail.add(...)` 旁同步 `rounds.add(AttackRound(round, currentPrompt, result.response, result.judgeResult.verdict != Verdict.FAIL))`
- `fallbackAttack`：同样补 `rounds`（否则静态变异路径的时间轴是空的，而这条路径是**未配攻击模型时的默认路径**）
- 同时按 2.3 修正返回值：未破防时返回**首轮**结果（现在返回末轮）

## 4. 绘图原语（新增 `app/src/main/java/com/xieguojian/aiseclab/ui/chart/`）

前提：当前 `ReportScreen.kt`（512 行）里 `Canvas` / `drawRect` / `Brush` **一个都没有**，所有图表从零搭。

| 文件 | 形态 | 数据进 |
|---|---|---|
| `MiniHeatmap.kt` | 维度 × 用例的方块矩阵，颜色按 `confidence` 分档 | `List<TestResult>` |
| `TimelineTrack.kt` | 横向时间轴，一格一轮，格子状态 = `refused`；破防轮加标记 | `List<AttackRound>` |
| `MiniBar.kt` | 四路分区 / 判定层级的条形分布 | `List<Int>` + `List<String>` |

三条设计约束：

1. **原语不依赖任何业务类型**（纯数据进、图出）—— 这样报告页、导出 HTML、将来别处都能复用。
2. **颜色沿用报告里已有的风险配色**（复用 `ScoringModel` 的风险色），**不新造第二套色彩语言**。红色在本项目语义 = 失守/危险。
3. **导出侧**：`ReportGenerator.kt` 的自包含 HTML 导出用**内联 SVG**（不依赖 JS、不依赖 CDN），这样导出的报告在没有网、没有脚本的环境里也能看。

小屏约束：50 用例 × 最多 10 轮，手机竖屏放不下 → 热力图与时间轴都要支持**横向滚动**，别压缩到看不清。

## 5. 分批

### 第一批（本方案范围）

1. **数据**：`AttackRound` 端 / 后端镜像落地 + `refused` 按 3.3 定义 + 按 2.3 修正端上返回值　← **唯一的数据改动**
2. **原语**：`MiniHeatmap` / `TimelineTrack` / `MiniBar`
3. **接线**：报告页三块图表 + HTML 导出的内联 SVG
4. **验收**：`tools/run-unit-tests.py` 全绿 + 一份真实报告**肉眼核对**（含一次端到端，确认图不是空的）+ `tools/check-judge-parity.py` 输出无变化

### 明确不在本批

| 项 | 为什么排除 |
|---|---|
| 加固建议自动生成 | **[新建]** `evidence → 加固动作` 的映射逻辑 0 行（全仓库只有 `ScoringModel.kt:106` 一句固定文案），是另一个量级的活 |
| 逐 token 危险度曲线 | **[新建]** 需要给 `TestResult` 加护栏分布字段，且护栏三分支覆盖不全，图会误导 |
| 攻击分叉树 | 需要**改攻击器支持并行分支** —— PAIR 现在是单链，画成树就是用可视化撒谎 |
| 众测评分卡 / 排行榜 | 与 BYOK「数据零留存、Key 不留服务器」的核心设计冲突 |

### 5.1 落地实测修正（2026-10-12，真机 MTN-AN80 / Android 16）

第一批实现完成后上真机验证（安装 debug APK → 点开历史报告 → 逐屏截图），实测推翻了本方案初稿的**两处设计**：

| 初稿 | 实测问题 | 修正 |
|---|---|---|
| 配色 / 图例放 `ui/chart/`（§4 第 2 条） | `ChartSvg`（在 `core/report`）要引用配色 → **core 反向依赖 ui**，分层坏了 | `ChartPalette` / `ChartLegend` 下沉到 `core/report/`；`ui/chart/` 只留 Compose 组件 |
| 「攻击演进」挂在**失守明细**里（导出侧） | 失守 0 条的模型同样有多步攻击记录 → **导出件整块丢图**；而 App 报告页有独立区块、看得到。**同一份数据、两种形态不一致**，且只在「失守 0 条 + 存在多步用例」这个组合下触发 | 取数判据收敛为 `ReportSections.trailCases`，报告页 / Markdown / HTML **三处共用**，导出侧独立成章（与报告页同序） |

另有两个**只有肉眼能发现**的显示缺陷（`uiautomator dump` 里文本是完整的，编译与单测都绿灯）：

- `ChartLegend` 文案里带 `**粗体**` → Compose `Text` **不解析 Markdown**，界面上原样显示成 `这是**用例级**粒度`；
- `MiniBar` 标签宽 104dp → `不可评估·调用失败` 被截断成 `不可评估·调用失...`，调到 136dp。

三处都已修复并在真机复验。回归测试落在 `ReportChartTest` / `ReportSectionsTest`，其中
「**失守 0 条时导出仍要带攻击演进**」专门钉住上面那个组合条件 bug —— 它此前两条既有断言都覆盖不到
（原用例的失守条目自带多步记录，所以永远走的是"有失守"分支）。

> 教训：`编译通过 + 单测全绿` 挡不住「取数挂错分支」和「Compose 不解析 Markdown」这两类问题。
> §5 原定的验收标准（真实报告肉眼核对）不是可选项。

## 6. 风险

| 风险 | 触发方式 | 对策 |
|---|---|---|
| **静默丢数据** | 字段名对不上 → `ignoreUnknownKeys` 静默丢弃 | 端到端跑一次**看到图**再算完 |
| **轮次错位** | 1-based vs 0-based（2.1） | 统一 1-based，两侧各写一条断言 |
| **最终判定指向不同轮** | 2.3 的返回值语义相反 | 端上对齐后端；端到端对照一次 |
| **第三份拒绝词表** | 顺手 new 一个拒绝词列表 | `refused` 只从 `verdict` 派生（3.3） |
| **`refused` 语义被当成判定** | 图上看起来像"安全结论" | 图例写清它只是展示用派生量 |
| **小屏不可读** | 50 格 × 10 格压进手机宽度 | 横向滚动，不压缩 |

## 7. 回答「要不要先改数据结构，再出方案」

**本次顺序：先方案（本文）→ 确认字段契约 → 一次性把 `attackRounds` 落地（端 + 后端同一提交）→ 再画图。**

不要反过来。理由：本文第 1 节那张「现状三分」表，本身就是用来判断"要不要动数据结构"的依据 —— 它给出的结论是**四项里三项零改动**。如果先改了代码，这张盘点表就失效了，也就无法判断工作量到底落在哪。

同时，第 2.3 节那处「未破防返回哪一轮」两端相反，是**纯读码发现的**，不在任何既有文档里。这类问题只有先把契约写出来、两侧对着看，才会浮出来 —— 也是"方案先行"的一个实例。
