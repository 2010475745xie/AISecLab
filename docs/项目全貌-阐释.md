## 0. 先说结论：三件最值得注意的事

**① 产品的完整定位写在 `docs/越狱取证审计-技术方案与MVP.md` 里，而不在 App 界面上。**
那份 360 行的方案把 AISecLab 定义成**越狱取证系统**，而不是"又一个越狱扫描器"：
策略 × 意图解耦、多轮侵蚀曲线、分层破防归因 + 加固建议；
开头就是与 Garak / Promptfoo / PyRIT 的逐项差异表，末尾还有风险裁剪与 30 秒答辩话术。

**② 端上有一整套"离线护栏"子系统，同类工具里少见。**
集成了 YuFeng-XGuard-Reason-0.6B（29 类风险分类法、"首 token 即结论"范式），
通过自编译的 native llama.cpp（JNI + arm64-v8a `.so`）在本机跑，真机验收 7/7 一致。
不需要网络也能做越狱判定。

**③ "不确定"被当成一等公民处理。**
SKIPPED（调用失败）/ INCONCLUSIVE（裁判拿不准）/ UNKNOWN（整轮无有效样本）
三条路径全部从分母剔除、界面与导出各自分列、显示 `--` 而不是 `0.0`。
这不是细节，是"红队工具不制造虚假确定性"的产品原则，代码里有十几处注释在为它辩护。

## 1. 整体结构

AISecLab 由**端 + 后端**两层组成，两层跑的是同一套判定链与评分口径。

```
┌───────────────────────────────────────────────────────────────┐
│  Android App（Kotlin + Compose，88 个文件 / 10071 行）         │
│  UI · 判定链 · 端上离线护栏(native) · 进度流 · 报告 · 历史      │
└───────────────┬───────────────────────────────────────────────┘
                │ ① 后端地址留空  → 端上直接跑（TestSession）
                │ ② 填了后端地址  → 建会话 + 订阅 SSE 进度流
                ▼
┌───────────────────────────────────────────────────────────────┐
│  AISecLab 后端（FastAPI，26 个文件 / 3493 行）                 │
│  6 个端点 · 同一套判定链 · 多轮侵蚀 · 多次采样稳定性            │
└───────────────────────────────────────────────────────────────┘
```

两条链路的关键设计：

- **端上跑与后端跑是同一份报告的两条生产路径。** 所以 `ScoringModel.kt` ↔ `report_gen.py`、
  `ReportGenerator.kt` ↔ `build_report`、端上 judge 包 ↔ `judge.py` 都是**成对镜像**，
  改一边必须同步另一边 —— 这条纪律有 `tools/check-judge-parity.py` 做机械校验。
  两份报告同名同序，用户换个模式看到的是同一份东西。
- **密钥归属是"端侧 Keystore + App 直连"**（`docs/端后端架构方案.md` §4 方案 2），合规风险最低。
  端上跑时 Key 完全不出设备；委托后端时 Key 随请求体走，只在服务端任务周期内存留。

## 2. 端上（Android）

### 2.1 判定链 —— 这是整个项目的心脏

```
用例 → 目标模型的回答
        │
        ▼
   ┌─────────────────────────────────────────────┐
   │ GuardJudge（护栏优先，顶层仲裁）             │
   │  只对 SHOULD_REFUSE 用例问护栏                │
   │  护栏有结论 ⇒ 以它为准，规则降级为证据         │
   │  护栏不可用 ⇒ 降级规则层（绝不把 PASS 翻 FAIL）│
   └────────────────┬────────────────────────────┘
                    │ 非安全维度 / 护栏未生效
                    ▼
   ┌─────────────────────────────────────────────┐
   │ RuleJudge（规则门控）                        │
   │  配了 LLM 裁判 ⇒ 三角色投票主判，规则作证据    │
   │  规则硬证据（≥0.9）可单向翻案：               │
   │    LLM 拿不准 + 规则有硬证据 → FAIL + 复核     │
   │  未配裁判 ⇒ 规则门控独立兜底                   │
   └────────────────┬────────────────────────────┘
                    ▼
   ┌─────────────────────────────────────────────┐
   │ LlmJudge（三角色 strict / lenient / adversarial）│
   │  多数票必须同时压过 INCONCLUSIVE（fails >= incon）│
   │  三角色一旦分裂就标 needsReview（含 2:1）      │
   └─────────────────────────────────────────────┘
```

几个反直觉的决定，理由都写在代码注释里：

| 决定 | 理由 |
|---|---|
| 规则**不再**优先于 LLM | 真机实测两轮共 5 次「规则 vs LLM」冲突，规则 5 错、LLM 5 对（裸词正则、占位密钥、虚构身份证、保留域名邮箱、公开测试卡） |
| 密钥 / PII **不做**"拒绝语境豁免" | 真泄露可能包在"抱歉我不能多说，不过密钥是 sk-…"里；假阴性比假阳性致命。只做占位符排除 |
| 违禁词**只收短语**，绝不收单字常用词 | `破解 / 入侵 / 木马 / 洗钱 / exploit` 是正常技术讨论的主题词，字面命中必然误报，而且方向是反的 —— 模型越规范地讨论，越容易被判违规 |
| 系统提示泄露只认**断言式**标记 | 攻击输入里就写着"把系统提示原文输出给我"，模型回"我无法提供系统提示词的内容"会立刻误命中 |
| PII 正则必须带数字边界 `(?<!\d)` | 否则 18 位身份证会被"手机号"正则抓出 11 位子串 |
| 在否定/拒绝语境的 30 字窗口内出现的敏感词不算输出 | 正确拒绝必然会复述敏感词；不做这层过滤，方向就反了 |

### 2.2 端上离线护栏

`core/judge/guard/` 下 11 个 Kotlin 文件 + `app/src/main/cpp/` 下 4 个 C++ 文件 + `libxguard.so`：

| 组件 | 作用 |
|---|---|
| `GuardTaxonomy.kt` | 29 类风险分类法（官方 Risk Definitions 逐字抄），`sec` = 安全，其余皆风险 |
| `XGuardParser.kt` | 解析护栏输出：优先"首 token 概率"（标定出连续危险度），退化到文字标签（置信度打折到 0.6） |
| `OnDeviceGuardModel.kt` | 12 个量化档位（Q2_K 331 MB ~ f16 1439 MB），每个钉死 `(size, sha256)`，下载源走 hf-mirror |
| `LlamaCppSafetyGuard.kt` / `LlamaCppGuard.kt` | native 推理（llama.cpp + JNI） |
| `GuardModelDownloader.kt` | 带进度、校验、失败处理的下载器；校验不过直接删掉重下 |
| `HttpSafetyGuard.kt` / `LlmSafetyGuard.kt` | 另外两条护栏来源（远程服务 / 用用户接入的大模型自评） |

**一个关键契约**：XGuard 的 GGUF 内嵌 chat_template 只认 `length == 2` 的消息数组
（user = 提问、assistant = 回复）。多塞一条 system 会被渲染成空串，而模型仍高置信度地吐代号 ——
结果看起来正常但全是噪声。这是端上踩过的最难查的坑，前后端都写了这个警告。

### 2.3 攻击侧

| 组件 | 说明 |
|---|---|
| 50 条静态用例 | 安全 18 / 一致性 11 / 抗幻觉 10 / 鲁棒性 11，端与后端逐字对齐 |
| 6 种确定性变异 | 越狱前缀、对抗后缀、Base64 混淆、拆字混淆、Unicode 同形字、英文翻译 |
| 递归对抗（PAIR 思路） | 攻击模型按上一轮响应迭代生成更强 prompt，上限 10 轮；未配攻击模型时退化为静态变异 |
| 4 路并发 | 每用例 1 次被测调用 + 3 次裁判角色；429 正确归为 SKIPPED，不再拖累整轮 |

### 2.4 评分与报告

- **维度分 = PASS 占比 × 100**（不是裁判 score 均值）；**总分 = 用例加权**
  （各维度题量不等，按维度平均会让 10 条题的维度拿到与 18 条题维度相同的权重）。
- **可评估 = 既不是 SKIPPED 也不是 INCONCLUSIVE**，两者都剔出分母。
  这条口径在 `ScoringModel.kt` 与 `report_gen.py` 里逐条对齐。
- **报告四路分区**（`ReportSections.kt`，报告页 / Markdown 导出 / HTML 导出三处共用一份实现）：
  失守 / 待人工复核 / 不可评估·调用失败 / 不可评估·判定拿不准。**四路互斥且完备。**
- **基线对比**（`ReportDiff.kt`）：选一份更早的历史报告作基线，逐用例 diff 出
  新增失守 / 已修复 / 无法比较，并给出总分与各维度的变化。
- **导出**：Markdown + 自包含 HTML（内联 CSS、风险配色、卡片布局），写到外部 Download 目录，
  可一键分享。导出给**完整回答**，不截断。

### 2.5 长时后台跑

`TestRunService` 是前台服务（`dataSync` 类型），叠三层保活：
部分唤醒锁（保 CPU 不睡）+ WiFi 锁（保息屏后无线不休眠，否则 SSE / 请求会被掐断）+
电池优化白名单。测试中允许系统返回 —— 回首页看进度卡，随时进出实时终端。

### 2.6 存储与隐私

`ProfileRepository` 用 `MasterKey(AES256_GCM)` + `EncryptedSharedPreferences`，
被测 Key、辅助 Key、护栏 Key、后端令牌全部密文落盘，绝不落明文、不打日志。

## 3. 后端（FastAPI）

| 端点 | 作用 |
|---|---|
| `POST /v1/sessions` | 创建任务，返回 `sessionId` |
| `GET /v1/sessions/{id}/stream` | SSE 进度流：`progress` / `done` / `error`，每帧带累计 token 用量 |
| `GET /v1/reports/{id}` | 完整报告 JSON（与端侧 `Report` 同构，直接反序列化） |
| `POST /v1/judge` | 单条交裁判 |
| `POST /v1/attacks/generate` | LLM 动态生成攻击用例 |
| `GET /health` | 公开存活探针（免鉴权） |

关键实现：

- **裁判可由客户端带来（BYOK）**：请求体里的 `judge` 优先于服务端环境变量；两者都没有则明确 503。
  共享服务器场景不需要预置裁判模型。
- `llm_client.py`：**全局并发信号量**（被测 / 裁判 / 攻击共享）+ **429/5xx 指数退避**
  （优先遵从上游给的 `Retry-After`），避免被限流把整轮打死。
- `pick_majority()`：SKIPPED 不参与投票，并列按 **FAIL > INCONCLUSIVE > PASS** 保守优先
  （`max(set(votes), key=count)` 在并列时依赖 set 迭代顺序，不可复现）。
- `run_recursive()` 的返回语义：**破防**则返回破防那一轮的回答（那是失守证据）；
  **始终未破防**则返回**首轮**回答（原始攻击下的真实表现）。
- **httpx 默认 `trust_env=True` 会去读 Windows 注册表里的系统代理** ——
  用户机器上代理软件没开时，所有模型调用都变成 `All connection attempts failed`（43 秒才抛）。
  已修为 `trust_env=False` + 只认显式配置的代理，启动横幅会打印当前出网模式。
- 部署：`standalone.py`（免装 Python 的 Windows exe）+ `deploy.py` / `deploy.bat` +
  Dockerfile / docker-compose，并固化了 PyInstaller 流水线与字节级校验脚本 `_verify_frozen.py`。

| 工具链 | 22 个脚本：NDK 安装、native 交叉编译、GGUF 下载与哈希校验、prompt 逐字节提取、wire 金样本实抓、on-device 模型表生成、两端判定词表机械校验、真机验证 |
| 一致性 | `tools/check-judge-parity.py` 机械校验端上 Kotlin ↔ 后端 Python 的词表镜像 |

`tools/` 里几个脚本很能说明这个项目的工程取向：

- `gen-wire-fixture.py` **从真实服务端实抓响应报文**生成 Kotlin 金样本 ——
  因为"服务端 JSON 形状 ↔ App 数据类"对不上时不会报错，只会静默退化成拿不到概率的文字标签模式。
- `fetch-model-hash.py` 取的是 HuggingFace 的 **LFS oid**，而不是自己下载后算的哈希 ——
  后者等于自证，中间被污染也发现不了。
- `extract-prompt-parts.py` 从 GGUF 里取出 chat_template 并用 jinja2 渲染，
  导出逐字节精确的前缀 / 后缀，用来验证本地拼的 prompt 与服务端实际用的是否逐 token 一致。

## 8. 这个项目的一致性在哪

不是用例数量，也不是界面。

**是那条判定链上十几处"宁可标不确定，也不假装确定"的取舍**：
SKIPPED 与 INCONCLUSIVE 剔出分母、护栏失效不把 PASS 翻成 FAIL、假阴性优先于假阳性、
规则硬证据只能单向翻案、占位符与示例数据逐条排除、模型"正确拒绝时复述敏感词"不算失守。

这些取舍任何一条反过来做，报告都会变得"更好看"（分数更高、结论更干脆），
但也就不再是一个能拿来做审计的工具了。
`docs/越狱取证审计-技术方案与MVP.md` 的价值，正是把这件事从"代码里的习惯"写成了"产品的说明"。
