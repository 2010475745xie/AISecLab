# AISecLab 端后端架构方案

> 决策日期：2026-09-29
> 决策内容：**安卓前端 + 后端代理**；判定架构**保留规则门控**
> 依据：谢国健确认的路线图（11 模块）+ 现行 Android 端代码

---

## 1. 架构决策

| 层 | 技术栈 | 职责 |
|---|---|---|
| 端（App） | Kotlin / Compose | UI、L1 规则预筛、进度流展示、可视化、本地缓存 |
| 后端 | FastAPI / 云函数 | 被测模型调用、攻击模型、裁判模型、多轮侵蚀、LLM 裁判、策略聚类 |

**判定架构：保留规则门控** —— 规则置信度 ≥ 0.9 直接定论（端侧预筛，省一次网络往返）；
< 0.9 交后端 LLM 裁判三角色（strict / lenient / adversarial）出结论。

这意味着路线图第 6 条维持原样，**上一轮讨论的"删规则改 LLM 主裁"方案作废**。
代价是现行判定链的 5 个已知缺陷必须在架构期修干净（见 §6），否则搬到后端要修两遍。

## 3. API 协议草案（端 ↔ 后端）

认证：App 启动换取后端 token（阶段一可先用固定 API Key + 强制 HTTPS）

```
POST /v1/sessions                      创建测试任务
  req : {target:{baseUrl,model,apiKey?}, aux?, guard?, dimensions:[],
         recursive:bool, dynamicAttack:{enabled,count}, attackBudget}
  resp: {sessionId}

GET  /v1/sessions/{id}/stream          SSE 进度流
  event progress {completed,total,dimension}
  event verdict  {caseId,verdict,confidence,level,evidence[]}   ← 逐条实时回推
  event done     {reportId}
  event error    {message}

GET  /v1/reports/{id}                  完整报告 JSON（与端侧 Report 模型同构）

POST /v1/judge                         单条交裁判（端侧预筛不确定时）
  req : {caseId,prompt,response,ruleEvidence[]}
  resp: {verdict,confidence,evidence[],needsReview,disagreements[]}

POST /v1/attacks/generate              生成攻击用例（路线图第 5 条）
  req : {dimension,strategy,count}
  resp: [{id,dimension,strategy,prompt,expected}]
```

**关键约束：判定口径单一来源。** `Verdict` / `TestCase` / `Report` 的 JSON schema、
规则置信度阈值（0.9）、`FAIL_SET` 映射表，必须两端同构，用一份共享契约文件维护 ——
否则端侧预筛和后端裁判会给出互相打架的结论。

## 4. 密钥归属（**必须先定**）

### 方案 1：密钥交后端保管（KMS / Secret Manager）
- 优点：App 只调后端，链路最简单；被测 / 裁判模型统一由后端调
- 缺点：**代用户保管第三方 API Key 是敏感行为** ——
  - 后端需 ICP 备案（国内服务器）
  - 隐私政策必须明示代持行为与责任边界
  - 泄露风险由平台承担
  - 上架华为应用市场时属于审核关注点

### 方案 2：密钥只存端侧 Keystore，App 直连被测模型
- 优点：合规风险最低（密钥不出设备）；后端不碰用户 key；规则部分可离线
- 缺点：端侧要自己实现 OpenAI 协议调用 + 并发（现有代码可复用）；
  后端仍需裁判模型 key（平台自有，风险可控）；
  每条用例从手机出网，流量 / 耗电上升，弱网稳定性差

**推荐：方案 2 起步** —— 合规风险最低、现有端侧调用代码可直接复用；
等平台化 / 多用户场景再评估方案 1。

## 7. 落地顺序（建议）

| 阶段 | 内容 | 估时 |
|---|---|---|
| 0 | **定契约**：Verdict / TestCase / Report schema + 阈值表，两端共享 | 1-2 天 |
| 1 | 后端骨架：FastAPI + `/sessions` + `/judge` + SSE，先用假数据打透协议 | 3-5 天 |
| 2 | 判定链搬迁：`LlmJudge` 三角色、`AttackEngine`、递归攻击重写为 Python；用现有 51 条用例做**对拍回归**（同输入下端侧规则与后端结论一致） | 5-8 天 |
| 3 | 端侧改造：`TestRunService` 改订阅 SSE、报告渲染接后端 JSON | 3-5 天 |
| 4 | 路线图第 5 / 8 / 10 / 11 条（策略标签、代际进化、工具注入、基准对比） | 8-11 天 |
| 5 | 路线图第 7 条可视化（**依赖第 5 条的数据结构**） | 3-5 天 |

**工时**：路线图 30 天是纯功能量；加后端平台（协议 + 部署 + 双端一致性验证 + 密钥方案落地），实际 **45-55 天**。
